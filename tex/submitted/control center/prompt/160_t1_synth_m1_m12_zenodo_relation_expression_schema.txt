The SIARC project has 5 existing Zenodo deposits (PCF-1 concept `19931635`; PCF-2 concept `19936297`; Channel Theory concept `19941678`; D2-NOTE concept `19996689`; Umbrella concept `19885550`) and 12 program axes M1-M12 (per slot 159 canonical outlook `M1_M12_CLOSURE_OUTLOOK_20260510_POST_OPEN_ITEMS.md`). | M2 / M3 / M5 / M11 / M12 | NOT-YET-OPENED (RULE 1 tabled) | — |
| M4   | V0 closed | bridge `5f9db69` cascade 106; folded into PCF-2 v1.4 |

| M10  | V0 OPEN | Lean sorry discharge work-stream (slot 148 first-halt); SAFE-phrased commitment in Umbrella v2.3 Appendix C ii |

Slot 157 verdict §Q4b set the deposit cascade as Option α' (PCF-2 v1.4 → Umbrella v2.3) but did NOT prescribe how M-axis structure is expressed in deposit metadata. Existing slot 137 PCF-2 v1.4 substrate-prep (`zenodo_v14_description_block.md` §2) carries 3 Related-identifier rows (`IsNewVersionOf` PCF-2 v1.3; `IsSupplementTo` PCF-1 concept; `Cites` PCF-1 concept) and a v1.4 changelog paragraph that mentions M7 cascade `7f93b9e` in prose. There is no axis-coverage table.

This consultation addresses three interlocking questions:

1. Is the existing native-vocabulary pattern sufficient for the Option α' deposit cascade?
2. Should an axis-coverage table with controlled vocabulary be standardized across all SIARC Zenodo deposits?
3. Should slot 160 itself be a standalone schema-lock fire, or is the schema small enough to fold inline into F6 (Umbrella v2.3 substrate-prep) and PCF-2 v1.4 deposit description at deposit time?

The agent's pre-consultation 3-layer scheme (sketched in session 2026-05-10 ~20:30 JST):
- **Layer 1**: Native Zenodo Related-identifiers (paper-tier; machine-parseable)
- **Layer 2**: Description-embedded "Program-axis coverage" table with controlled status vocabulary (axis-tier; human-readable)
- **Layer 3**: SIARC Zenodo Community (program-tier; discoverability) — gated by F5 / D-157-7

## §3 The 6 questions

### Q1 — Native Zenodo Related-identifier vocabulary sufficiency

The current slot 137 PCF-2 v1.4 description block carries 3 Related-identifier rows. After slot 157 Option α', a 4th row is implied:
```
IsNewVersionOf  10.5281/zenodo.19963298    PCF-2 v1.3
IsSupplementTo  10.5281/zenodo.19931635    PCF-1 concept
Cites           10.5281/zenodo.19931635    PCF-1 concept
IsSupplementTo  10.5281/zenodo.19885550    Umbrella concept    ← NEW per Option α'
```

**Q1a.** Is this row set sufficient for PCF-2 v1.4 OR are additional rows required to express M-axis cross-references? If additional rows are required, enumerate them (e.g., `IsSupplementTo`/`Cites` rows for Channel Theory `19941678`, D2-NOTE `19996689`, picture v1.19 deposit at bridge `70d1a48`).

**Q1b.** For axis-tier closure references (M4 cascade `5f9db69`, M7 cascade `7f93b9e`, etc.) — is `References` with a GitHub permalink (`https://github.com/papanokechi/siarc-relay-bridge/tree/<SHA>/sessions/...`) appropriate, or should these be expressed in the Description body only? Address GitHub URL stability concerns (rebase risk, repo rename risk) versus archival best practice.

**Q1c.** Is the concept-DOI vs version-DOI discipline (per memory `substrate verification`: "Cross-link IsSupplementTo should target concept-DOI not version-DOI") correctly applied in the proposed row set? Are there any cases where version-DOI is the right target despite the general rule?

### Q2 — Layer 2 axis-coverage table standardization

**Q2a.** Should every SIARC Zenodo deposit Description embed a structured "Program-axis coverage" table (M1-M12 with status column)? Or is this redundant given Layer 1 already encodes paper-tier relations and the canonical outlook (slot 159) is citable?

**Q2b.** If standardized, what is the minimal controlled vocabulary for the status column? Agent's pre-proposal:

```
covered (V0-closed; primary)    -- this deposit is the canonical home for the closed axis
covered (V0-closed; folded)     -- this deposit absorbs the closed axis but a primary exists elsewhere
partial                          -- this deposit covers part of the axis; full closure pending
not in scope                     -- axis not addressed in this deposit
external                         -- axis lives in a different deposit; cite that deposit
tabled (RULE 1)                  -- axis is RULE-1-tabled; not yet opened
retired (into Mx)                -- axis was retired into another axis (M3→M4, M5→M6.CC)
```

Synth: lock, amend, or replace this controlled set?

**Q2c.** Granularity question: should the table list M1-M12 atomically, or group RULE-1-tabled axes (M2/M3/M5/M11/M12) as a single row?

### Q3 — Layer 3 SIARC Zenodo Community

**Q3a.** Is creating a SIARC Zenodo Community now (under RULE 1, since Community creation is admin-tier infrastructure not a deposit) appropriate, or should it be deferred to post-RULE-1-lift (`F5` blocked, `D-157-7` operator decision)? Re-evaluate D-157-7 with slot 159 canonical outlook context.

**Q3b.** If/when created, should the Community description carry a master M1-M12 axis status snapshot (and update on axis flips), or should each deposit's Description carry the snapshot independently?

### Q4 — Forward-compatibility

**Q4a.** When M2 / M3 / M5 / M11 / M12 axes open post RULE 1 lift (currently 5 tabled axes), how should existing deposit metadata be amended? Options: (i) Zenodo "new version" with updated axis-coverage table; (ii) Description amendment via Zenodo edit (no version increment); (iii) leave existing deposits frozen and rely on newest-deposit table being authoritative.

**Q4b.** What is the intended lifetime of bridge cascade SHA references (`References` rows pointing to GitHub commit URLs)? If `siarc-relay-bridge` is ever renamed or rebased, what is the migration path?

### Q5 — Slot 160 fire/no-fire binary

This is the meta-question. The agent's pre-consultation default position is **NO-FIRE**: fold the controlled vocabulary directly into F6 Umbrella v2.3 substrate-prep + amend PCF-2 v1.4 description block at deposit time. Rationale: schema is small (~15 lines markdown); standalone bridge fire is governance overhead with thin payoff.

**Q5a.** Synth: confirm or contradict the NO-FIRE default. If FIRE is preferred, justify by enumerating the consumers + reusability gain.

**Q5b.** If FIRE is preferred, what minimum-viable scope for the slot 160 fire? Three options:
- **MIN**: just lock the Layer 2 controlled vocabulary (~1 markdown deliverable)
- **MED**: Layer 2 vocabulary + reference Layer 1 row-pattern + Layer 3 deferral note (~3 deliverables)
- **MAX**: Layer 1 + 2 + 3 full schema with sample tables for PCF-2 v1.4, Umbrella v2.3, and a future M1 D2-NOTE update (~5 deliverables)

**Q5c.** If NO-FIRE is preferred, what minimum-viable artefact captures the schema in lieu of a fire? Options:
- (i) inline schema in F6 prompt body (Umbrella v2.3 substrate-prep)
- (ii) one-paragraph addendum to slot 137 `zenodo_v14_description_block.md` operator-side amendment
- (iii) absorb into operator runbook only; no in-repo schema artefact
